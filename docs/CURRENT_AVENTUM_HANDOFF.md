## 1. Project Identity

**Name:** Aventum.

**One-sentence definition:** an AI Payment Incident Intelligence Agent for merchant-facing payment operations — it detects, diagnoses, simulates, and safely resolves payment disruptions, combining evidence-backed root-cause analysis with human-approved recovery actions (source: `README.md`).

**Problem being solved:** when a payment gateway degrades, someone has to notice, work out why, decide whether rerouting traffic would help, and act — today done manually and slowly. Aventum automates detect→diagnose→explain→simulate→recommend, while keeping execution behind mandatory human approval.

**Target user / positioning:** a merchant-facing payment-operations tool, built as a high-fidelity, production-shaped prototype for a Razorpay-style buildathon.

**Complete product workflow (locked, unchanged since Day 1):**
```
Detect → Diagnose → Explain → Simulate → Recommend → Human Approve → Execute → Verify → Audit
```

**What Aventum is NOT — the honesty boundary (non-negotiable, restated in almost every doc in `docs/`):** it must never claim real Razorpay production telemetry, real Razorpay gateways, real production routing decisions, real production credentials, actual recovered GMV, or real live payment execution. The system is production-**shaped**, not production-**connected**. Every synthetic/simulated value carries explicit provenance labeling designed to make this structurally hard to violate (§5, §23).

**AI model vs. AI agent vs. deterministic analytics vs. simulator vs. safety/control plane — how Aventum keeps these distinct:**
- **Deterministic analytics** — anomaly detection, evidence computation, RCA scoring (`aventum_incident`, implemented).
- **Simulator** — the Day 2B synthetic-infrastructure generator (implemented) and the Day 4A counterfactual simulator (not yet implemented) — both are deterministic, not LLM-driven.
- **Safety/control plane** — the deterministic policy gate (Day 4A, not yet implemented) — thresholds are code constants, never agent-writable.
- **AI agent** — Qwen3 8B via Ollama (Day 4B, not yet implemented, not even installed as a repo dependency) — interprets and orchestrates, never calculates authoritative numbers.
- **AI model** — Qwen3 8B itself is just the underlying model; "agent" is the tool-calling loop built around it. Neither exists in the repository yet.

No row of the Nigerian file is ever attached to a UPI `transaction_id`.

## 5. Truth / Epistemic Model

**Important reconciliation, not silently resolved:** two versions of this model exist in the repository, from different points in the project's history, and they are not worded identically.

- **`docs/DAY2B_TRUTH_MODEL.md`** (written during Day 2B, before Day 3 existed) defines a table headed "The four layers" that actually lists **five** rows (an original-document internal inconsistency, preserved here rather than silently fixed): (1) Observed fact, (2) Synthetic infrastructure state, (3) Synthetic *observed signal* (latency/response/attribution — a Day-2B-specific concept, distinct from Day 3's later "simulated incident outcome"), (4) Incident ground truth (marked "does not exist yet — Day 2C" at the time it was written), (5) Agent conclusion (marked "does not exist yet").
- **`docs/DAY3_ARCHITECTURE_REVIEW.md` line 145** restates the model in its Day-3-complete, final form, which is the version this handoff and the Day 4 contracts use: **"observed fact (`transactions`), synthetic infrastructure attribution (Day 2B), simulated incident outcome (`simulated_*`), incident ground truth (isolated table), and RCA prediction (`incident_rca_results`)."**

**Authoritative interpretation for all future work:** use the DAY3_ARCHITECTURE_REVIEW.md five-layer form. It supersedes the Day2B doc's version because it is later and reflects Day 3's actual addition of the simulated-incident-outcome layer, which did not exist when DAY2B_TRUTH_MODEL.md was written.

### The five layers (final form)

| Layer | What it is | May enter it | May leave it | Must NEVER enter it |
|---|---|---|---|---|
| **1. Observed fact** | `transactions` — real UPI rows, read-only forever | Nothing (fixed at ingestion) | Read by every downstream layer, as evidence | A model-generated value |
| **2. Synthetic infrastructure** | Gateway identity, health, calibrated failure probability — `synthetic_*` tables | Calibration-informed design parameters | Read by simulation/detection, always labeled `synthetic_*` | An unlabeled write into `transactions` |
| **3. Simulated incident outcome** | `simulated_incident_outcomes` — the Approach-B incident-period layer | Modelled degradation for the incident window/cohort only | Read by detection/evidence/RCA | A reallocation of any observed status |
| **4. Incident ground truth** | `incidents.ground_truth_root_cause` / `incident_ground_truth` table | The known-by-construction cause of an injected scenario | **Only** an offline evaluation/scoring step, after RCA has already run | Any diagnosis, detection, RCA, agent, or recommendation code path — this is audited by AST scan plus adversarial deleted/corrupted re-runs (`docs/DAY3_IMPLEMENTATION_REPORT.md`) |
| **5. Agent conclusion** | `incident_rca_results` today; future `recommendations`/Qwen rationale | Deterministic RCA output today; Qwen's qualitative rationale in Day 4B | Presented to a human, always labeled as inference | Re-entry as evidence for any later stage — it is an output, never an input |

**Non-negotiable statements, verbatim from `docs/DAY2B_TRUTH_MODEL.md` §"Statements Aventum may and may not make":**
- **May NOT say:** "These are real Razorpay gateways/routing decisions/latencies/error codes"; "These are observed UPI gateway logs"; "The Nigerian dataset is production telemetry"; "Gateway C causes more failures" stated as real-world fact; "This simulated outcome is what actually happened."
- **MAY say:** "In Aventum's synthetic infrastructure model, gateway_C carries a calibrated baseline failure probability of 6.21%"; "This transaction was observed to fail; the synthetic model attributes it to gateway_C with an infrastructure-side response code" (note the register: **observed** outcome, **attributed** infrastructure, labeled differently in the same sentence).

**Status-conditioned attribution (the one modelling decision that most needs stating plainly):** Day 2B samples gateway assignment from the posterior `P(gateway | observed status)`, not the prior `P(gateway)` — `P(g|FAILED) ∝ w_g × p_g`, `P(g|SUCCESS) ∝ w_g × (1−p_g)`. This preserves observed marginals exactly (no failure created or destroyed) and converges per-gateway failure rate to the calibrated `p_g` (verified at 4σ). It does **not** claim any gateway caused any particular failure, and does not constitute evidence that gateway differentiation exists in real UPI. "It constructs a plausible infrastructure world consistent with observed data — it does not discover one."

## 6. Day 1–2 Foundation (implemented, package locations)

**`backend/aventum_ingest/`** — canonical transaction ingestion.
- Atomic load via `transactions_staging` (truncated start/end of every run, never read downstream); promotion only after full validation.
- Idempotency: identical source SHA-256 is detected and skipped (`SKIPPED_IDEMPOTENT`); `--force` re-executes and converges on the same fingerprint rather than duplicating rows.
- Quarantine: every rejected row is logged to `ingestion_rejects` with source row index, failing rule, offending fields, and the full raw payload — never silently discarded (0 rejects on the audited source, measured).
- Schema-drift protection and dataset identity: `source_dataset` resolves from SHA-256 via `dataset_registry`, **never from filename** — an unregistered file's hash is refused before anything is written (exit code 5).
- `ingestion_run_id` provenance link added Day 2A (P1 fix) so every canonical row traces to the exact run that produced it.

**`backend/aventum_synth/`** — synthetic infrastructure baseline (Day 2B).
- 5 gateways (`gateway_A`..`E`), each `is_synthetic=true` (DB `CHECK`-enforced, not just documented), calibrated against the Nigerian-dataset rails (§4).
- Deterministic RNG (`aventum_synth/rng.py`) — same seed reproduces the identical fingerprint exactly (live-reconfirmed: 4 generation runs, 3 with identical fingerprint marked `SUPERSEDED`, the 4th `SUCCEEDED`, all four sharing fingerprint `e8414edd…52fe3c8`).
- Coherence chain enforced by generation code **and** DB `CHECK` constraints: `observed status → response family → latency regime → latency value`. Impossible combinations (`SUCCESS`+failure response, `FAILED`+`APPROVED`, `TIMEOUT` response outside `TIMEOUT` regime, `APPROVED`+`issuer_side` attribution) are DB-rejected. `APPROVED`+`ELEVATED` latency is **deliberately permitted** (a slow-but-successful payment is realistic — forbidding it would hand a later RCA shortcut that wouldn't exist in reality).
- Provenance mechanisms (four, all machine-enforced, not just documented): `synthetic_`-prefixed table names; `is_synthetic` with `CHECK (is_synthetic = true)` on all six synthetic tables; `v_transaction_infrastructure` view prefixing every column `observed_*`/`synthetic_*` plus explicit `transaction_provenance`/`infrastructure_provenance` markers; calibration provenance stored as data (`calibration_source_rail`, `calibration_reference_name` per gateway).
- Health windows, staleness rules: `synthetic_gateway_health_states` is the intended lever for later degradation (used by Day 3); `baseline-v1` gateway profiles and routing policy are **never mutated** — new versions get added instead (cross-cutting rule, restated in `docs/5_DAY_EXECUTION_PLAN.md`).

**Cross-dataset PK note:** `transactions.transaction_id` (text PK) is the join key `synthetic_infrastructure_assignments` and `simulated_incident_outcomes` both hang off; no numeric surrogate key is used anywhere in the transaction lineage.

## 7. Day 3 Final State

**Package:** `backend/aventum_incident/` — `cli.py`, `constants.py`, `detect.py`, `evaluation.py`, `evidence.py`, `handoff.py`, `hypothesis.py`, `incident.py`, `metrics.py`, `models.py`, `pipeline.py`, `rca.py`, `rng.py`, `scenarios.py`, `simulate.py`, `statistics.py`.

**Approach B (locked, non-negotiable):** `transactions.status` (and every other observed field) is never modified, overwritten, or reallocated. The incident period gets its own simulated-outcome layer (`simulated_incident_outcomes` — 14,651 rows live, across all 7 incidents combined) with its own provenance prefix. A degradation **adds** simulated failures to the affected cohort; it does **not** redistribute the 12,376 existing observed failures away from healthy gateways.

**Why Approach B was selected over the alternative ("reallocate observed failures"):** the Day 2B review measured that reallocating observed failures onto a degrading gateway at 25% severity drops the control group to **0.48× its baseline failure rate** — healthy gateways would appear to get *healthier* during an incident, which no real degradation does, and which would make RCA evaluation artificially easy (`docs/DAY2B_ARCHITECTURE_REVIEW.md` §Status-Conditioned Attribution Model, part D).

**Nine live tables** (vs. the four sketched in `docs/DAY3_IMPLEMENTATION_CONTRACT.md` — the contract's own amendment note explains why, and this handoff reconciles rather than re-derives):
`incidents`, `simulated_incident_outcomes`, `incident_ground_truth` (isolated — see below), `incident_anomalies` (detection), `incident_hypotheses` (competing explanations with supporting *and* contradicting evidence), `incident_rca_results` (the conclusion), `incident_evidence`, `incident_simulation_runs` (run-anchor for the simulate stage — confirmed live NOT a Day-4 counterfactual table; its columns are `simulation_run_id, incident_id, simulation_seed, incident_model_version, incident_config_version, status, rows_in_window, rows_simulated, rows_changed, simulation_fingerprint, model_parameters, started_at, finished_at, error_message, is_simulated` — 7 rows live, matching the 7 incidents), `incident_analysis_runs` (run-anchor for the detect→RCA stage).

**Ground-truth isolation:** moved to its **own table**, `incident_ground_truth`, rather than a flagged column on `incidents` — deliberately, because "a flag on a shared row is a convention and conventions leak through an incautious `SELECT *`; a separate table makes the isolation structural." Verified by AST scan plus adversarial deleted/corrupted re-runs; no diagnosis module imports or names this table.

**Eighth evidence type added after a measured failure:** `confounding_check` — a degraded gateway drags every dimension intersecting it, inflating rival hypotheses; this evidence type tests whether a cohort's anomaly survives excluding the leading suspect on another dimension.

**PRIMARY vs. DERIVATIVE alert roles (P1-1 fix):** only `PRIMARY` alerts are actionable root-level inputs; derivative anomalies remain queryable as shadow evidence (`derivative_detections`) but are never independent root causes. Evidence is never discarded to buy precision — `test_derivative_alerts_keep_their_evidence` asserts this.

**Confidence decoupling (P1-2 fix):** `confidence`, `evidence_strength`, `significance_sigma`, `severity` are stored as four separate columns on `incident_rca_results` (live-confirmed schema) and never collapsed into one scalar.

**Generalization / uncertainty testing:** `golden` (flagship, must name gateway_C), `quiet` (ordinary window, must stay silent), `alternative` (issuer-centred degradation, must **not** blame a gateway — proves the engine reasons from evidence, not a memorized answer) — all three run via `aventum_incident.cli scenarios`. Plus four more live incidents (`review-C` through `review-F`, `p1-independent`) used during the P1 review, one (`review-E-mild`) left `ACTIVE`/undiagnosed by design (a deliberately-too-weak signal).

**Ground-truth isolation enforcement (Non-Negotiable Rule 4 of the Day 3 contract):** `incidents.ground_truth_root_cause` is never referenced by any query in the detection or RCA code path — audited explicitly, described as "the epistemic boundary the whole project depends on."

## 10. Counterfactual Contract

**Held constant (enforced, not assumed):** transaction population; transaction IDs; transaction amounts; payment mix; cohort; incident; incident window; incident multipliers; gateway health state; gateway profile (`baseline-v1`); model/config versions; policy version; seed semantics; eligibility assumptions.

## 11. Simulation Semantics

**One authoritative success-probability model:** `P_success(t | g) = 1 − clamp(baseline_failure_probability[g] × health_failure_multiplier[g, window])`. Day 4A must reuse Day 3's exact funnel — a second, conflicting probability formula would violate the "identical inputs → identical outputs" determinism requirement running through the whole project.

**Candidate set, every simulation run:**
- `NO_ACTION` — **mandatory, always evaluated first**, with a real simulation (not a null row), so the comparison baseline is measured, not assumed.
- Bounded reroutes: **10% / 20% / 30%** of the affected cohort, to each eligible healthy gateway.
- **30% is a policy ceiling, not an optimality claim** — it is the largest shift that keeps every receiving gateway below the concentration cap in the flagship scenario (gateway_C carries 13.08% of traffic; 30% of it is ~3.9pp moving onto a peer). Documented as a prototype bound, explicitly not a claim about real payment infrastructure.

**NO_ACTION as a first-class success state:** must remain reachable when evidence is insufficient, benefit is too small, risk is too high, the target is unavailable, the simulation is invalid, policy blocks intervention, or no candidate beats `NO_ACTION` by the required margin. The system must never be structurally biased toward acting.

**Fingerprints:**
- `input_fingerprint` — SHA-256 over every held-constant input (§10) plus model/config versions and seed; re-derived at **recommendation time and again at execution time**; any mismatch ⇒ `STALE_SIMULATION`, execution rejected, re-simulation required. This is the direct structural answer to red-team scenario 10 ("simulation inconsistent with its inputs") — a *derived* check that cannot be bypassed by editing a status column.
- `simulation_fingerprint` — distinct field on `counterfactual_simulations`, identifies the specific simulation output itself.

**Capacity/eligibility limitation carried into simulation output (see §9, §13, §21):** `capacity_utilization` always `NULL`, `"capacity": "UNAVAILABLE"` in `assumptions`; eligibility reported as `ELIGIBILITY_UNCONDITIONAL`.

## 12. Optimization / Business Objective

**Primary — maximize expected GMV retained:**
```
expected_gmv_retained(policy) =
    Σ  amount_t × ( P_success(t | target_gateway) − P_success(t | current_gateway) )
   t ∈ rerouted
```
Every term is read from Day 2B profiles, Day 2B health states, and observed `transactions.amount` — no term is estimated by the agent.

**Secondary:** expected success-rate delta on the affected cohort.

**Tie-break:** prefer the *smallest* traffic shift achieving ≥95% of the best candidate's GMV retention — "the system prefers the least intervention that captures nearly all the benefit."

**Selection rule:**
```
best = argmax(expected_gmv_retained) over PERMITTED candidates
if best.expected_gmv_retained < NO_ACTION_MARGIN: → NO_ACTION
```
Qwen may explain the ranking; Qwen may not alter the objective, weights, or margin.

**Projected vs. actual — the vocabulary boundary that must never blur:** simulation output must never be called "recovered GMV." Approved terms: *projected GMV retained*, *estimated GMV retained*, *GMV at risk*, *simulated benefit*. "Recovered" implies verified real-world outcome, which Day 4A cannot produce (no real execution exists) and which even Day 5's "verification" will itself be a simulated continuation, not a live feed (per `docs/5_DAY_EXECUTION_PLAN.md`'s own Day 5 caveat).

## 13. Risk / Policy

**Risk model — deterministic, explicit, fail-closed, independent of Qwen; never a blended opaque score.** Separate measurable dimensions preserved where derivable: concentration risk, target-health risk, latency risk, simulation-quality risk, evidence uncertainty, routing uncertainty. Unavailable inputs remain `UNAVAILABLE`, never silently assumed away.

**The 13-gate deterministic policy table (verified verbatim against `docs/DAY4_EXECUTION_CONTRACT.md` §2 during this extraction):**

| # | Gate | Requirement | Reason code |
|---|---|---|---|
| 1 | RCA verdict | `CONFIDENT` | `RCA_NOT_CONFIDENT` |
| 2 | RCA confidence | ≥ 0.60 | `CONFIDENCE_BELOW_THRESHOLD` |
| 3 | Evidence strength | ≥ 0.50 | `EVIDENCE_STRENGTH_BELOW_THRESHOLD` |
| 4 | Significance | ≥ 6.0σ | `SIGNIFICANCE_BELOW_THRESHOLD` |
| 5 | Severity | CRITICAL or HIGH | `SEVERITY_BELOW_THRESHOLD` |
| 6 | Alert role | `PRIMARY` | `ALERT_NOT_PRIMARY` |
| 7 | Simulation status | `VALID` | `SIMULATION_INVALID` |
| 8 | Simulation freshness | `input_fingerprint` matches now | `STALE_SIMULATION` |
| 9 | Target eligible | `is_eligible = true` | `TARGET_NOT_ELIGIBLE` |
| 10 | Target healthy | `HEALTHY` across the whole window | `TARGET_NOT_HEALTHY` |
| 11 | Traffic shift | ≤ 30% | `TRAFFIC_SHIFT_EXCEEDS_BOUND` |
| 12 | Post-action concentration | ≤ 40% | `CONCENTRATION_EXCEEDS_BOUND` |
| 13 | Expected benefit | ≥ `NO_ACTION_MARGIN` | `BENEFIT_BELOW_NO_ACTION_MARGIN` |

**All gates must pass.** Thresholds are constants in `aventum_policy` — not parameters the agent, the recommendation, or the approval payload can influence. Runs at `DRAFT → PERMITTED|BLOCKED` and **again at execution**.

**Why confidence+evidence_strength+significance+severity are required together, not any one alone:** "the direct consumption of Day 3's P1-2 fix: no single scalar can authorize an intervention" — this is a load-bearing consequence of a real defect found and fixed in Day 3, not a design preference.

**Capacity is explicitly NOT a gate** (§9 P1-1) — no capacity data exists; inventing one would be exactly the kind of fabricated production value the project's honesty rules forbid.

## 14. Recommendation / Approval / Execution

**Recommendation lifecycle:**
```
DRAFT ──► PERMITTED ──► AWAITING_APPROVAL ──► APPROVED ──► EXECUTED
  │           │                 │                 │
  └► BLOCKED  └► SUPERSEDED     └► REJECTED       └► EXPIRED
                                                  └► ABANDONED
```
`NO_ACTION` terminates at `PERMITTED` — no approval, no execution required, and this is a **successful** outcome, not degraded. **TTL: 30 minutes** from creation.

**Recommendation integrity (the structural anti-fabrication property):** quantitative fields originate **only** from the persisted simulation. The recommendation builder receives a `simulation_id` and reads every quantitative value server-side; the agent-facing tool (`propose_action`) accepts **no numeric fields at all**. Agent-generated content is limited to qualitative rationale/citations. Verified structurally, not by convention — this is red-team scenario 1's defense.

**Human approval:** every non-`NO_ACTION` intervention requires it. Append-only, fingerprint-bound, expiring, human-associated. Qwen can *request* approval (tool 9, `request_human_approval`) but cannot decide it. The approval JSON payload example in `docs/DAY4_EXECUTION_CONTRACT.md` includes an explicit `"provenance": "SYNTHETIC_INCIDENT / SIMULATED_EXECUTION"` field, so the approval record itself carries the honesty boundary, not just surrounding prose.

**Simulated execution:** `SimulatedRoutingAdapter` (designed, not coded) — future production boundary `RoutingActionAdapter`. Must: accept only approved actions; **revalidate current state** (not trust the in-memory/handed-in approval object); enforce bounds/eligibility/health again; enforce idempotency; emit an audit event; produce a measurable simulated result. Must not claim successful recovery during Day 4A — Day 5 owns verification.

**9-step execution revalidation (before any execution proceeds):** re-read persisted recommendation; re-read persisted approval; check expiry; check approval fingerprint; re-derive `input_fingerprint` and compare to the simulation's stored value; re-run the **full** 13-gate policy; re-check policy version; re-check target health; re-check target eligibility; check action idempotency. Any single failure → `REJECTED`, **no override path**.

**Action idempotency:** `idempotency_key = SHA256(recommendation_id ‖ approval_id ‖ adapter_name)`, UNIQUE at the database level on `actions`. A second execution call **returns the first result** — the adapter is invoked exactly once. This is the structural defense against duplicate/concurrent execution (red-team scenario 8).

## 16. Qwen / Agent Design

**Status: PLANNED — NOT YET IMPLEMENTED.** No `ollama`/`qwen` dependency exists in `backend/requirements.txt`; no `aventum_agent` package exists; this was independently confirmed by inspecting the live repository tree during this extraction, not merely re-quoted from a prior claim.

**Model / runtime:** Qwen3 8B, local Ollama, target hardware RTX 4050 Laptop (6,141 MiB VRAM). Fixed runtime options: `{"model": "qwen3:8b", "think": false, "temperature": 0, "format": "json"}`.

**`think:false` is a hard architectural requirement, empirically derived, not a stylistic default:** with thinking enabled, the model spent its entire 64-token budget on chain-of-thought and returned an **empty response** in 8,124 ms; disabled, it returned valid structured JSON in 1,273 ms. Do not change this default without re-running the same measurement on the target hardware.

**Exact authority split:**
- **Qwen may:** interpret evidence; choose tools; compare tool results; explain tradeoffs; formulate qualitative rationale; recommend `NO_ACTION`; identify uncertainty.
- **Qwen may NEVER:** calculate authoritative numbers; invent simulation results or risk; alter safety thresholds; approve actions; bypass policy; execute actions; access ground truth; access unrestricted SQL or raw transactions.

**Context discipline:** Qwen never receives raw transactions. It receives the incident summary, the RCA object, at most 20 evidence records, gateway health for ≤5 gateways, and simulation summaries — "a few KB of JSON, comfortably inside 8,000 tokens, and nowhere near the 250,000-row dataset."

**Resource budget (measured on the target hardware, not assumed):**

| Budget | Limit |
|---|---|
| Agent turns | 12 |
| Tool calls / incident | 20 |
| Simulations / incident | 8 |
| Context to Qwen | ≤ 8,000 tokens |
| Per-turn Qwen timeout | 30 s |
| Tool timeout | 10 s (30 s for `run_counterfactual`) |
| Total agent timeout | 180 s |
| Incident → recommendation | < 300 s |

Exceeding any budget → `BUDGET_EXCEEDED`, recommendation `ABANDONED`, audit event — no fabricated fallback.

**Qwen-unavailable degradation:** a deterministic recommendation can still be produced with `rationale = NULL` — simulations and the policy gate are agent-independent (this is red-team scenario 7, "SAFE DEGRADATION").

**Prompt-injection defense:** tool outputs are delivered in a `tool` role, treated as untrusted data; safety thresholds are code constants unreachable from any prompt; the agent has no tool that can change limits, approve, or execute — worst case from malicious text in evidence/transaction fields is a suspicious rationale *string*, which cannot move a number or pass a gate (red-team scenario 5).

**No RAG / vector DB / long-term memory** — explicitly forbidden. Minimum persistent state: `agent_runs` (budget, status) and `agent_tool_calls` (what was seen). Nothing carries across incidents.

## 21. Known Limitations

- No capacity telemetry exists anywhere in the schema (`UNAVAILABLE`, §9/§13).
- `eligibility_conditions` is NULL/unconditional for all 5 gateways (`ELIGIBILITY_UNCONDITIONAL`, §9/§13).
- No failure is ever in the `NORMAL` latency regime (Day 2B P2-1, inherited into Day 3 P2-2) — makes latency- and failure-rate-based detection perfectly redundant in one direction; does not currently distort RCA (hypothesis engine doesn't key on raw latency) but would bias a future latency-based detector.
- Static, single-snapshot dataset (2024 UPI CSV) — no live feed exists; Day 5's own "verification" is necessarily a simulated continuation, not a real post-action measurement (`docs/5_DAY_EXECUTION_PLAN.md` Day 5 §3).

**Synthetic-data limitations:** every infrastructure/incident field is 100% synthetic by construction (`docs/FIELD_PROXY_ANALYSIS.md`) — this is a deliberate design choice (§1), not an unnoticed gap, but it bounds every downstream claim to "modeled," never "measured."

**Production-integration limitation:** no real routing adapter exists; `RoutingActionAdapter` is a documented future interface, not code (§9, §14).

**Model/hardware limitations:** VRAM headroom is only 250–760 MiB with Qwen3 8B loaded — "works today," but `AGENT_UNAVAILABLE` degradation path exists specifically because this margin is tight (Day4 pre-flight P2-1).

**Statistical limitations:** UNCERTAIN verdict band (between CONFIDENT and INSUFFICIENT) is defined but never exercised end-to-end — all current scenarios land CONFIDENT or INSUFFICIENT (Day 3 P2-9, closed as a side effect of the P1-2 fix but still structurally unexercised).

**Classification — BLOCKER vs. DEFERRED vs. KNOWN LIMITATION:**
- **BLOCKER (none currently open):** the pre-flight review found 0 P0 issues; both P1s have a documented, already-decided resolution.
- **DEFERRED (safe to leave, revisit only if evidence demands):** all P2 items listed in §22.
- **KNOWN LIMITATION (permanent, not a defect to fix):** the honesty-boundary constraints themselves (no capacity data, no live feed, synthetic infrastructure) — these are inherent to the buildathon-prototype framing (§1) and are not expected to be "fixed," only honestly reported.

## 23. Security / Safety Invariants (non-negotiable, cuts across every phase)

1. `transactions` is immutable forever — no code path may write to it after Day 2A load.
2. `baseline-v1` gateway profiles and routing policy are never mutated — new versions are added, never edited in place.
3. Incident ground truth never enters any diagnosis, detection, RCA, agent, or recommendation code path — evaluation-only, structurally isolated (own table, AST-scanned).
4. Deterministic systems calculate; Qwen interprets/orchestrates; policy constrains; only a human approves; only the execution adapter acts (§9 authority chain).
5. Qwen cannot alter safety thresholds, invent numbers, approve, execute, or access ground truth/raw transactions/unrestricted SQL.
6. The policy gate is fail-closed — any of the 13 gates failing blocks the action, with no override path.
7. Every non-`NO_ACTION` intervention requires human approval; approval is append-only, fingerprint-bound, and expires (30-minute TTL).
8. Execution never trusts an in-memory/handed-in approval object — it re-reads persisted state and re-runs the full 9-step revalidation, including the full policy gate again, every time.
9. Action idempotency is enforced at the database level (`UNIQUE` on a SHA-256 key) — duplicate/concurrent execution produces exactly one adapter call.
10. Audit is append-only — no update/delete path is exposed for the audit trail.
11. No production claims: no real Razorpay telemetry/gateways/routing/credentials/recovered GMV/live execution, ever (§1) — enforced by four machine-checked provenance mechanisms (table naming, `is_synthetic` CHECK constraints, `observed_*`/`synthetic_*` view prefixes, calibration provenance stored as data), not documentation alone.
12. New randomness anywhere uses the Day 2B deterministic RNG architecture — never an unseeded `random` or Python's salted `hash()`.
13. Dataset identity resolves from SHA-256 content hash, never filename — an unregistered file's hash is refused before anything is written.
